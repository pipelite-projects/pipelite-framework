= Message and Headers
:description: The Message payload container and the Headers shared across a flow

== Message

A `Message` (package `io.pipelite.core.exchange.internal`) is the container for the application
payload - one for the input of the `Exchange`, and, once produced, one for its output. It carries
the payload itself, its type and a correlation id, nothing else - it has no metadata of its own,
that role belongs to `Headers`, which lives on the `Exchange` rather than on either `Message` (see
below).

A `Processor` never needs to hold a `Message` reference directly: `exchange.getInputPayload()` /
`getInputPayloadAs(Class)` read the input message's payload, and `exchange.setOutputPayload(Object)`
writes the output message's payload - see xref:core:exchange.adoc[Exchange].

NOTE: The id of a message changes from one step of the flow to the next, and is not the same when the application restarts and gives a message back: it is not a key to hand to an external system. For that, see the xref:exchange.adoc#_idempotency_key[idempotency key] of the exchange.

The payload is shared, not copied, when an exchange is handed to several places: see <<_what_is_copied_and_what_is_shared,What is copied, and what is shared>>.

== Headers

`Headers` are string key-value pairs that live on the `Exchange` itself, not on the `Message` -
there is a single set of headers per exchange, and neither its input nor its output `Message`
knows anything about them.

=== Read

[source,java]
----
Headers headers = exchange.getHeaders();

// Optional read
Optional<String> value = headers.tryGetHeader("x-request-id");

// Read with expectation (throws NoSuchElementException if absent)
String value = headers.expectHeader("x-request-id");

// Typed read
Optional<Integer> n = headers.tryGetHeaderAs("retry-count", Integer.class);

// Presence check
boolean present = headers.hasHeader("x-request-id");
----

=== Write

[source,java]
----
headers.putHeader("x-correlation-id", "xyz-789");
headers.removeHeader("x-temp");
----

Headers survive across the whole flow: whenever an `Exchange` advances to the next node, the
framework carries a copy of the current headers into the new `Exchange` - a header set at any
step is still visible in every step downstream.

== Headers from and to the outside

A request that arrives, a Kafka record that is read, and the message a flow writes to another system carry headers of their own: `Idempotency-Key`, `X-Tenant-Id`, a trace id. A flow chooses which of them cross the border, with `propagateHeaders(...)` on the settings of the source for the ones that come in, and on the settings of the sink for the ones that go out. It is the same for every channel adapter that has headers.

[source,java]
----
Pipelite.defineFlow("orders")
    .fromSource("http://orders", (HttpSourceConfigurer c) -> c
        .propagateHeaders(h -> h.filter("Idempotency-Key", "X-Tenant-Id")))   // <1>
    .process("charge", (exchange, contribution) -> {
        String tenant = exchange.expectHeader("X-Tenant-Id");
        // ...
    })
    .toSink("kafka://paid-orders", (KafkaSinkConfigurer c) -> c
        .propagateHeaders(h -> h.filter("Idempotency-Key")))                   // <2>
    .build();
----
<1> Only these two headers of the request go on the exchange.
<2> Only this header of the exchange is sent with the record.

* *By default no header crosses the border.* The headers of a request carry credentials (`Authorization`, cookies, tokens), and the headers of an exchange are written to disk with it: they end up in the durable inbox, in the dumps of a failure and in the dead letter queue. A flow takes the ones it needs.
* *`filter(...)` names the headers, and the case of the name is ignored.* The header has on the other side the name written in the flow, so the flow does not depend on how a client spelled it: `idempotency-key` arrives as `Idempotency-Key`.
* *`all()` lets every header cross.* Use it only when the flow really needs them all, and know that credentials will be among them.
* *A header is text.* A number, a boolean or an enum on the exchange is sent as its text; any other value is not sent.
* *A header that is not there is not an error.* The exchange simply does not have it.

NOTE: `propagateHeaders(...)` exists only on the settings of an endpoint that has headers: `http://` as a source, `kafka://` as a source and as a sink. An endpoint with none (a file, a timer, a log) does not offer it, so the flow does not compile; and `queue://` does not either: an exchange that goes through a queue keeps all its headers.

Besides its headers, what a channel adapter knows about the request or the record is offered in the same way, with names of its own: see xref:channel-adapters:http.adoc#_headers_of_the_request[HTTP] and xref:channel-adapters:kafka.adoc#_headers_of_the_record[Kafka].

== Headers vs. payload

Both travel through the flow together, but for different reasons:

* Use *headers* for information *about* the message that a downstream step needs to decide *what
to do*, without caring what the message actually contains - e.g. a `priority` or `region` header
that a `filter` or `toRoute(...)` uses to send an order down a different path depending on
where it came from, regardless of what is inside the order itself. They are cheap to read
(`Headers['name']`) and are exactly what `filter` and `toRoute(...)` are built around (see
xref:dsl:expressions.adoc[Expressions]).
* Use the *payload* for the actual content being processed - e.g. the `Order` object itself, with
its line items and total, that each `Processor` reads, transforms or replaces. It is what the
pipeline exists to move and change; headers are metadata riding along with it, not a second place
to put application data.

A simple test: if a value is something you would filter or route on without touching the business
object, it belongs in a header; if it is the data your processors' logic actually reads or
produces, it belongs in the payload.

== What is copied, and what is shared

Where the framework hands an exchange to more than one place - the destinations of `toRoute(...)` and `toRecipientList(...)`, and `wireTap(...)` - each one receives an `Exchange` of its own: the headers and the properties are copied, and the message is a new one. The *payload* is not cloned: it is the same object in every copy, and so are the values of the properties. It is the same object from one step of a flow to the next, too, because the output of a step is the input of the following one.

[cols="1,2"]
|===
|Copied |Shared

|The `Exchange` and its message, the headers (their values are scalars, so nothing is shared), the properties (the entries, not their values)
|The payload object, and the values of the properties
|===

So treat the payload as a *value*: do not change an object you received, set a new one with `exchange.setOutputPayload(...)`. If you do change it, every flow that got the same object sees the change, on its own thread, in no particular order and with no error. When a destination has to change an object that another destination has too, it makes a copy of it first, at the start of its flow.

NOTE: Through `queue://` the receiving flow gets the very instance of the `Exchange` that the sender handed over, see xref:channel-adapters:queue.adoc[Queue Channel Adapter].
