= Split
:description: Splitting a collection payload into one exchange per element, each continuing through the flow on its own

Pipelite supports the *Splitter* Enterprise Integration Pattern with the `.split(name)` method of the DSL. A message that carries a collection is broken down into one exchange per element, and each element goes on through the steps that follow the split, exactly as if it had arrived on its own.

== Basic usage

[source,java]
----
FlowDefinition flow = Pipelite.defineFlow("order-batch-flow")
    .fromSource("http://orders/inbound")
    .split("split-orders")                          // <1>
    .process("validate", orderValidator)            // <2>
    .process("enrich", orderEnricher)
    .toSink("kafka://orders-processed")             // <3>
    .build();
----
<1> `.split(name)` takes the payload of the exchange, which must be a `Collection`, and sends each element on as an exchange of its own.
<2> The steps after the split run once for each element, in the order of the collection.
<3> So does the sink: here every order is published on its own.

An element can go anywhere a message can go, because nothing about a split limits what follows it. The scenario that used to need a second flow and a call to `supplyExchange` is written in the flow itself, a split followed by a recipient list:

[source,java]
----
.process("list-items", ...)                         // the items as a List payload
.split("open-items")                                // one exchange per item
.toRecipientList("queue://job-a-requests", "queue://job-b-requests", "queue://job-c-requests")
----

or, to send each element where it belongs, followed by `toRoute(...)`.

== What an element is

Each element is an `Exchange` with the element as its payload, and:

* the *headers* of the exchange that was split, and the headers of the split (below);
* its *properties*, the ones that belong to the work: the return address, the routing slip and the properties of your application. It does not carry the entry of the durable inbox of the exchange that was split (that one is acknowledged once, when the split has been sent on), nor the state of its attempts, so it starts with no failure and no retries behind it;
* an xref:core:exchange.adoc#_idempotency_key[idempotency key] of its own, the key of the exchange followed by its position (`<key>-0`, `<key>-1`, ...), the same each time the split is run again.

Changing the headers of one element never changes the others, or the exchange that was split. The payload objects are the elements of the collection themselves and are not copied: see xref:core:messages.adoc#_what_is_copied_and_what_is_shared[What is copied, and what is shared].

=== The headers of the split

Each element carries three headers, defined as constants in `io.pipelite.dsl.split.SplitHeaders`:

[cols="2,1,3"]
|===
|Header |Type |Content

|`Pipelite-Split-Id`
|`String`
|The id of the split: the same for every element of one run of the split.

|`Pipelite-Split-Index`
|`Integer`
|The position of the element in the collection, from zero.

|`Pipelite-Split-Size`
|`Integer`
|The number of elements.
|===

They are headers like any other: a step can read them, and `toRoute(...)` can use them in an expression. They leave the flow only if it asks for them with `propagateHeaders(...)`.

== Behavior

* The elements go *one after the other*, in order, on the thread of the flow. The split returns when the last element has gone through the rest of the flow.
* An *empty collection* is valid: no element is produced and nothing continues after the split.
* A payload that is not a `Collection` is a failure of the split step, handled by the error handling of the flow like any other.
* The execution of the exchange that was split ends when the last element has gone through. The barriers that await the flow, the key of an ordered source and the acknowledgement of the durable inbox are released then. If the application stops before, the exchange is delivered again and split again, and the idempotency keys of the elements are the same.

== When an element fails

A step that fails for an element is handled for that element, by the error handling of the flow (see xref:core:error-handling.adoc[Error Handling]):

* With `.withRetry(...)`, `.withErrorChannel(...)` or `.withExceptionHandler(...)`, the failure is retried or dead-lettered *on its own*, resuming at the step that failed with that element, and the other elements go on. A retry never repeats the elements that already went through.
* Without any of them the default handler logs the failure and stops that element, and the other elements go on.

NOTE: Putting the elements back together into one exchange is not something a split does. A step that collects exchanges into a batch is a separate one.
