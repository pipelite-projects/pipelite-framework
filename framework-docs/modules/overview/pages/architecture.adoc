= Architecture
:description: Internal architecture of the Pipelite Framework, components and their interactions

[#seda-design]
== SEDA Design

Pipelite is based on a message-oriented pipeline architecture: each *flow* represents a processing path that starts from a *source*, passes through one or more *processors*, and ends at a *sink*. Communication between nodes occurs through `Exchange` objects that encapsulate the in-transit message.

[source]
----
Source Endpoint
      │
      ▼
[Exchange: input Message + Headers + Properties]
      │
      ▼
Processor Node 1  ──── WireTap ──► Side Channel
      │
      ▼
Processor Node 2 (transform / filter / route)
      │
      ▼
Sink Endpoint
----

More fundamentally, Pipelite is a *Staged Event-Driven Architecture* (SEDA): a flow is not one function call from source to sink. It is a series of independent stages, each with its own queue and its own thread, that hand `Exchange` instances to one another. Understanding this is essential before relying on any assumption about timing or ordering — it is easy to write code that *looks* synchronous but isn't.

=== Decoupled by design

Separating "accepting a message" from "running the pipeline for it" is the whole point of SEDA: each stage can absorb bursts, apply back-pressure, and keep running even while another stage is momentarily backed up, instead of one slow step freezing everything upstream of it.

The natural side effect of that separation is timing: accepting a message — an HTTP `201`, a Kafka record polled, a `link://` send returning — only means it has been queued for its stage, not that the pipeline has run yet. If your code assumes a downstream side effect (a file written, a database row inserted, a second flow having run) is already visible as soon as the accepting call returns, it is assuming a synchronous call that this architecture deliberately doesn't make.

=== One stage, one queue, one thread

Every event-driven source (HTTP, Kafka, Link) works the same way: accepting an event and running the pipeline are two *separate* steps, connected by a queue.

The thread that accepts the event (Undertow's request thread for HTTP, the Kafka poll thread, the sending flow's own thread for a `link://` hop) only ever does the *enqueue* step, then moves on immediately. For an HTTP source, this means the response is sent back to the caller as soon as the `Exchange` is queued — *before* a single processing step of the pipeline has run. A different, dedicated thread (or a shared worker pool, when the source declares `?concurrency=N` — see xref:dsl:flow-definition.adoc[Flow Definition]) is the one that actually dequeues the `Exchange` and runs the pipeline.

The queue is bounded (a fixed capacity). If the pipeline can't keep up, the queue fills up and the accepting thread blocks on enqueue until there's room — this is the framework's back-pressure mechanism, not a bug.

`main-flow` finishes its own execution (including the `link://` handoff) without waiting for `secondary-flow` to do anything. `secondary-flow` runs whenever its own dedicated thread gets around to dequeuing — normally milliseconds later, but under load, or if `secondary-flow` is backed up, later than that.

=== What this means in practice

* Don't treat "the source accepted the message" (an HTTP `201`, a Kafka record polled, a `link://` send returning) as "the flow finished". It only means the `Exchange` was queued.
* Don't assume strict ordering across stage boundaries when a source declares `concurrency > 1` — Exchanges dequeued around the same time can finish processing in any order.
* A slow consumer on one stage creates back-pressure on *that stage's* queue only — it does not block unrelated flows, but it does delay anything still waiting to be enqueued onto it.
* xref:core:processors.adoc[WireTap]'s behavior depends on its destination: forwarding to an external sink (`slf4j://`, `http://`, `kafka://`) runs *synchronously* on the same thread, so a slow destination there delays the main flow. Forwarding to another flow (`.wireTap("audit", "link://audit-flow")`) goes through the exact same queue handoff described above — the wiretapped flow runs asynchronously, on its own thread, same as any other `link://` hop.

See xref:internals:flow-lifecycle.adoc[Flow Lifecycle Internals] if you need the full implementation-level detail behind this model.

== Core Components

=== PipeliteContext

The `PipeliteContext` is the central container of the framework.
It is responsible for:

* Registering the `FlowDefinition` objects produced by the DSL.
* Instantiating `Flow` instances from their definitions.
* Managing the framework lifecycle (start / stop).
* Resolving `ChannelAdapter`s for endpoint URLs.

[source,java]
----
PipeliteContext context = Pipelite.createContext();
context.registerFlowConfigurationClass(MyFlowConfiguration.class);
context.start();
----

For simple inline definitions, direct registration via `registerFlowDefinition` is also supported.

=== Flow

A `Flow` is the execution unit of a pipeline.
Each flow is associated with a source `Endpoint` that produces `Exchange` objects and a chain of `FlowNode` instances that process them sequentially.

=== Exchange

The `Exchange` is the message transport container along the flow.
It contains:

* `input` — The incoming `Message` with payload and headers.
* `output` — The response `Message` (optional).
* `headers` — Shared metadata across nodes (`Headers`).
* `properties` — Context properties (routing slip, return address, etc.).

=== Message

A `Message` carries the application payload with its own headers.
The payload can be any serializable Java type.

=== Endpoint

Each `ChannelAdapter` produces `Endpoint` instances.
An `Endpoint` can expose:

* A `Consumer` (event-driven or polling) to receive messages from the source.
* A `Producer` to send messages to the destination.

=== FlowNode

`FlowNode` instances are the nodes in the processing chain — the DSL methods covered in xref:dsl:flow-definition.adoc[Flow Definition] (`.process(...)`, `.transformPayload(...)`, `.filter(...)`, `.wireTap(...)`, `.toRoute(...)`) each add one to the chain.

== Extensibility

Pipelite is built around a small set of public SPIs — most notably `ChannelAdapter`, for connecting a flow to a new external system. See xref:extensibility:index.adoc[Extensibility] for the complete reference.
