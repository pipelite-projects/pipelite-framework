= Flow Lifecycle Internals
:description: Internal components of PipeliteContext, detailed startup/shutdown sequence, FlowNode types, and threading model

WARNING: This page documents internal implementation details of Pipelite Framework, intended for contributors to the framework itself. It is *not* required reading to define, run, or extend flows as a user of the framework. See xref:core:flows.adoc[Flow and PipeliteContext] instead.

== Internal components

[cols="1,3"]
|===
|Component |Responsibility

|`FlowRegistry`
|Maintains the registry of all active `Flow` instances, indexed by name.

|`ChannelAdapterManager`
|Resolves `ChannelAdapter` instances via classpath scan and associates them with endpoint URLs.

|`EndpointFactory`
|Creates `Endpoint` instances by delegating to the correct `ChannelAdapter` based on the URL scheme.

|`ServiceManager`
|Starts and stops all registered `Service` instances (polling consumers, HTTP server, etc.).

|`ExchangeFactory`
|Creates new `Exchange` and `Message` instances with distributed identity.
|===

== Detailed lifecycle

[source]
----
PipeliteContext.start()
  │
  ├─ ChannelAdapterManager.initialize()
  │    └─ scan classpath → load ChannelAdapters
  │
  ├─ For each registered FlowDefinition:
  │    ├─ EndpointFactory.createSourceEndpoint()
  │    ├─ EndpointFactory.createSinkEndpoint()
  │    ├─ Build FlowNode chain (processors, transformers, routers)
  │    └─ FlowRegistry.register(flow)
  │
  └─ ServiceManager.startAll()
       ├─ Start EventDrivenConsumerService (HTTP, Link, Kafka, etc.)
       └─ Start ScheduledPollingConsumerService (Time, File, Retry)

PipeliteContext.stop()
  └─ ServiceManager.stopAll()
       └─ Orderly shutdown of all consumers
----

== FlowNode types

[cols="1,3"]
|===
|Type |Responsibility

|`DefaultProcessorNode`
|Execution of application logic via `Processor`

|`PayloadTransformerNode`
|Payload transformation via `PayloadTransformer`

|`MessageTranslatorNode`
|Message type translation (see xref:message-translation.adoc[Message Translation Internals])

|`ExpressionFilterNode`
|Expression-based filtering

|`WireTapProcessorNode`
|Forwarding of a copied `Exchange` to a secondary destination via `PipeliteContext.supplyExchange(...)` — synchronous I/O if the destination is an external producer, or an enqueue onto that destination's own queue if it is another flow (see Threading model below)

|`RouterNode`
|Content-based routing with a routing table

|`RecipientListRouterNode`
|Delivery to multiple recipients simultaneously

|`RoutingSlipRouterNode`
|Dynamic routing via routing slip

|`ReturnAddressRouterNode`
|Routing to the return address set on the Exchange
|===

== Threading model

* *Event-driven consumers* (HTTP, Link, and the receiving side of Kafka) decouple receiving from processing via a producer/consumer queue, not a synchronous call. `EventDrivenConsumer.process(exchange)` (the producer side) enqueues the `Exchange` onto a bounded `PriorityBlockingQueue` (default capacity 20) and returns immediately — for HTTP this means `DefaultHttpHandler` sends the response back as soon as the `Exchange` is enqueued, *before* the flow's pipeline has actually run. A separate dedicated thread, started by `EventDrivenConsumerService.doStart()` (`EventDrivenConsumerReceiveTask`), blocks on `queue.take()` and only then runs the pipeline (`dispatchToNext` → the `FlowNode` chain). Kafka's `KafkaConsumerTask` polls on its own dedicated thread and calls `consume()` the same way — so a Kafka-backed flow actually involves two threads: one polling Kafka, another draining the queue and running the pipeline.
* *Polling consumers* backed by `ScheduledPollingConsumerService` (Time, File, Retry) have no such queue: a single scheduled thread per source calls `receive()` then `process()` directly, inline, on the same thread, at a fixed period.
* *Concurrent sources* (`fromSource(...?concurrency=N)`, see xref:dsl:flow-definition.adoc[Flow Definition]) replace the dedicated receive thread with a `ConcurrentDispatchTask`: it still dequeues one `Exchange` at a time from the same producer/consumer queue, but instead of running the pipeline itself, it hands each one off (gated by a `Semaphore` sized to `N`) to one shared, bounded worker pool — so up to `N` Exchanges from that source can be in flight on pool threads at once, and overall thread usage stays bounded no matter how many flows opt in.
* *WireTap*'s behavior depends on its destination — `WireTapProcessorNode.process()` always calls `PipeliteContext.supplyExchange(...)` synchronously on the calling thread, but what happens next forks in two directions (`DefaultPipeliteContext.supplyExchange`): if the destination URL has a channel protocol resolved to a `ChannelAdapter` (`slf4j://`, `http://`, `kafka://`, ...), it builds a `Producer` and calls `producer.process(...)` directly — the I/O runs on the calling thread, so a slow destination delays the main flow. If instead the destination is another flow (a `link://` URL, or a bare name resolved via the flow registry), it calls `consumer.consume(exchange)` on that flow's own consumer — the same producer/consumer queue handoff as a regular `link://` hop (see below), so the wiretapped flow actually runs asynchronously, on its own separate thread.
* The `RetryService` (a dedicated single-thread `ScheduledPollingConsumerService`) handles retries on its own thread, with access to the `FlowExecutionDumpRepository` via its `RetryPollingConsumer`.
* Every framework-owned thread is named `pipelite-<role>-<identity>` (`DefaultThreadFactory`), where `identity` is normally the owning flow's name (e.g. `pipelite-kafka-order-ingest`) or, when there is no single owning flow (the shared source-worker pool, the singleton retry service), a per-factory ordinal instead (e.g. `pipelite-pool-3`) — so a thread dump shows at a glance what each thread belongs to.
