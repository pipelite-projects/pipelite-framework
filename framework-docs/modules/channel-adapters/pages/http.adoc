= HTTP Channel Adapter
:description: Undertow-based HTTP adapter for inbound and outbound communication

The `http-channel-adapter` module implements an inbound HTTP server based on *Undertow 2.2.x*.

== Dependency

[source,xml,subs="attributes+"]
----
<dependency>
    <groupId>{project-group-id}</groupId>
    <artifactId>http-channel-adapter</artifactId>
    <version>{project-version}</version>
</dependency>
----

== Usage as source (inbound)

[source,java]
----
Pipelite.defineFlow("http-inbound")
    .fromSource("http://ingress")     // <1>
    .process("handle", (exchange, contribution) -> {
        String body = exchange.getInputPayloadAs(String.class);
        exchange.setOutputPayload("OK");
    })
    .toSink("slf4j://log")
    .build();
----
<1> Opens an HTTP listener on port 8080 (default) at path `/ingress`.

A request is answered only once the framework has accepted its exchange (written to the durable inbox and queued, applying the backpressure of the flow). If the exchange cannot be accepted, the request is answered with `500`.

The same `method` restriction can be applied through the typed `HttpSourceConfigurer` instead of a
query string (see xref:custom.adoc[Custom Channel Adapters] for the general mechanism):

[source,java]
----
.fromSource("http://orders", (HttpSourceConfigurer c) -> c.method("POST"))
----

=== Headers of the request

The headers of a request do not reach the flow unless the flow asks for them, see xref:core:messages.adoc#_headers_from_and_to_the_outside[Headers from and to the outside]. Besides the headers the client sent, with the name the client wrote, the adapter offers what it knows of the request with these names:

[cols="1,3"]
|===
|Name |Value

|`Http-Query-<name>`
|A parameter of the query, decoded: `?orderId=7` is `Http-Query-orderId`. A parameter that is repeated arrives as one value, separated by a comma.

|`Http-Method`
|The method of the request: `POST`.

|`Http-Path`
|The path of the request, without the query: `/orders`.
|===

[source,java]
----
.fromSource("http://orders", (HttpSourceConfigurer c) -> {
    c.propagateHeaders(h -> h.filter("Idempotency-Key", "Http-Query-orderId"));
    c.idempotencyKey(k -> k.headerName("Idempotency-Key"));     // <1>
})
----
<1> A request that the client sends again with the same `Idempotency-Key` is the same piece of work and has the same xref:core:exchange.adoc#_idempotency_key[idempotency key]. The name in `headerName` is the one written in `filter`, spelled the same way.


A header that the client sent with several values arrives as one value, with the values separated by a comma. A client cannot set `Http-Method`, `Http-Path` or a parameter of the query itself by sending a header with that name: the adapter always writes them after the headers.

WARNING: The query can carry tokens, and a header `Authorization`. Ask only for what the flow needs, since the headers of the exchange are written to disk with it.

=== URL format

[source]
----
http://<path>[?method=<HTTP method>]
----

[cols="1,1,3"]
|===
|Parameter |Default |Description

|path
|(required)
|The HTTP path on which the server listens (e.g. `/api/v1/events`)

|method
|(unset - any method accepted)
|Restricts this resource to a single HTTP method (e.g. `POST`). A request with a different method receives a `405`; a request to an unmapped path entirely receives a `404`.
|===

The Undertow server is started automatically by `HttpChannelAdapter.onContextStarted()` upon the first registration of an HTTP consumer.

=== Adapter-wide configuration

Port, host and the maximum size of a single request body are shared by every `http://` source in
a context - one Undertow instance serves all of them - so they are configured once, adapter-wide,
the same way Kafka's `bootstrapServers` is:

[source,java]
----
context.addChannelConfigurer((HttpChannelConfigurer) configuration -> {
    configuration.setPort(8443);
    configuration.setHost("127.0.0.1");
    configuration.setMaxEntitySize(1024 * 1024); // bytes
});
----

With Spring Boot, register it from a bean implementing `PipeliteContextInitializer` instead - see
xref:spring-integration:configuration-properties.adoc[Configuration Properties]. A plain `@Bean`
returning an `HttpChannelConfigurer` is *not* picked up automatically.

[cols="1,1,3"]
|===
|Setting |Default |Description

|port
|8080
|The Undertow listener's TCP port.

|host
|`0.0.0.0`
|The interface Undertow binds to.

|maxEntitySize
|10 MiB
|Upper bound on a single request's body size, in bytes. A request exceeding it receives a `413`
response instead of being read into memory unbounded.
|===

WARNING: `HttpChannelAdapter` has no built-in authentication and does not terminate TLS - it is
not safe to expose directly on an untrusted network. Put a reverse proxy (nginx, an API gateway,
a load balancer) in front of it to handle TLS termination and authentication before traffic
reaches this adapter.

== Usage as sink (outbound)

Not implemented yet: the HTTP endpoint has no producer (it keeps the default of `Endpoint#createProducer()`, which throws `UnsupportedOperationException`), so `.toSink("http://...")`/`.toChannel("http://...")` fail at flow-registration
time. `http-channel-adapter` is inbound-only today.

== Multiple path registration

Multiple paths can be registered on the same server:

[source,java]
----
context.registerFlowDefinition(
    Pipelite.defineFlow("flow-orders")
        .fromSource("http://orders").toSink("slf4j://orders").build()
);
context.registerFlowDefinition(
    Pipelite.defineFlow("flow-payments")
        .fromSource("http://payments").toSink("slf4j://payments").build()
);
----

`HttpChannelAdapter` maintains a per-path consumer map and shares a single Undertow instance.

WARNING: Registering two flows on the same HTTP path is not allowed: `IllegalStateException` will be thrown.
