= Testing
:description: BDD-style testing kit for Pipelite processors and flows

The `pipelite-test-support` module provides a fluent, BDD-style test kit for verifying Pipelite components in isolation or as end-to-end flows — without needing to wire a running container, configure real endpoints, or write boilerplate setup code.

== Maven dependency

Add `pipelite-test-support` to your project in `test` scope:

[source,xml,subs="attributes+"]
----
<dependency>
    <groupId>{project-group-id}</groupId>
    <artifactId>pipelite-test-support</artifactId>
    <version>{project-version}</version>
    <scope>test</scope>
</dependency>
----

== Single import

All factory methods are aggregated in `PipeliteTest`.
One static import is enough for an entire test class:

[source,java]
----
import static io.pipelite.test.PipeliteTest.*;
----

== Two testing modes

=== Processor mode

Tests a single `Processor` lambda in complete isolation — no runtime, no endpoints, fully synchronous.
Use this for unit-testing individual processing steps without bootstrapping the Pipelite engine.

[source,java]
----
given(
        header("Source-System", "Legacy-API"),
        inputPayload(Map.of("price", 100)))
    .when(process(myProcessor))
    .then(isSuccess(), payloadEquals(Map.of("price", 110)));
----

=== Flow mode

Tests one or more `FlowDefinition` objects running inside a managed `DefaultPipeliteContext`.
The fixture starts the context, injects the exchange into the specified entry-point endpoint,
waits for the exchange to travel the entire pipeline to its sink, then stops the context.

[source,java]
----
FlowDefinition flow = Pipelite.defineFlow("order-flow")
    .fromSource("orders-in")
    .process("validate", (io, c) -> { /* ... */ })
    .process("enrich",   (io, c) -> { /* ... */ })
    .toSink("kafka://orders-out")  // <1>
    .build();

given(
        flowDefinition(flow),
        header("X-Tenant", "acme"),
        inputPayload(order))
    .when(supplyTo("orders-in"))
    .then(isExecutionCompleted(), payloadEquals(expectedOrder));
----
<1> Real sinks (Kafka, HTTP, …) are automatically redirected to an internal `test://` capture endpoint.
The Kafka adapter is never instantiated during the test.

== Verifying intermediate steps

Use `step(stepName, ...)` inside `then(...)` to assert the exchange state captured *after* a named step executed, without interrupting the pipeline.

[source,java]
----
given(
        flowDefinition(flow),
        inputPayload("raw-input"))
    .when(supplyTo("in"))
    .then(
        output(isExecutionCompleted(), payloadEquals("final-value")),   // <1>
        step("normalize", payloadEquals("normalized")),                  // <2>
        step("enrich",    hasHeader("X-Enriched-By")));                  // <3>
----
<1> `output(...)` groups assertions on the final exchange captured at the sink.
<2> `step("normalize", ...)` asserts the snapshot taken *after* the `normalize` step.
<3> Multiple step assertions can be mixed with output assertions in a single `then(...)`.

If a step was never reached (e.g. because a previous step called `stopExecution()`),
`then(...)` throws `AssertionError` with a descriptive message.

=== Disambiguating same-named steps across linked flows

When multiple linked flows share a step name, use the two-argument form `step(flowName, stepName, ...)`:

[source,java]
----
.then(
    step("flow-a", "transform", payloadEquals("A")),
    step("flow-b", "transform", payloadEquals("B")));
----

== The BDD chain

[source]
----
PipeliteTest.given(Precondition...)  ─►  WhenOperations
                                              │
                                       .when(Action)
                                              │
                                              ▼
                                        ThenOperations
                                              │
                                       .then(Expectation...)
                                          ├── plain / output(...)  ─►  final exchange
                                          └── step(name, ...)      ─►  step snapshot
----

Each phase is fully parametric: preconditions, action, and expectations are passed as arguments, not chained as individual setter calls.

For the full API reference see xref:reference.adoc[API Reference].
